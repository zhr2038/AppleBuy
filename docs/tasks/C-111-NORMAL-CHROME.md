# C111 normal Chrome desktop connection, read-only first

Codex implements and tests. The user reports that normal Chrome can sign in while the programme browser cannot, asks to restart the programme and to use normal Chrome, and supplies the installed extension's public identifier. The desktop was actually restarted; no purchase or retained-session mode was started. A normal DOM-only bag observation was empty, but it does not prove account identity or settle the prior unknown addition.

Prepare a supported Chrome Native Messaging connection between this desktop application and the existing AppleBuy extension. Pin one extension origin in a current-user host registration, default to preparation only, and do not install or grant optional nativeMessaging before specific action-time approval. No personal-profile attachment, cookies, requests, password handling, authentication automation, extension/security-page control, stealth flags or validation bypass. The human-visible connector tab owns the connection; closing it disconnects. Original required extension permissions and no-background restriction stay intact.

This first milestone accepts only one fixed read-only operation: create an owned inactive official shopping-bag tab, require permitted host/complete document/two stable verified semantic reads, close only that tab, and return a bounded phase and matching-one-product boolean. No raw page/customer data enters native messages or logs. The desktop holds its existing task owner, requires a genuine permanently read-only imported record, never writes it, and cannot start/revive an old purchase. Missing permission, origin mismatch, timeout, malformed message, changed document or unconfirmed tab close must yield UNKNOWN, not an empty bag or safe retry.

During full regression the unchanged local FAKE DOM demo encountered fetch failures. Windows currently assigns ephemeral ports from a low range containing Fetch-forbidden ports; this is a supported possible cause, not retrospective proof of every older failure. A deterministic explicit-port reproduction failed before the fix. The demo now refuses an explicit forbidden port and closes/reallocates forbidden OS-assigned listeners at most eight times, with owner cleanup. OS/browser settings and all protected assertions are unchanged.

This is not Chrome installation/runtime evidence, login proof, a new buyer after an empty bag, automatic checkout, a slot hold/refusal or an unpaid order. Those remain the main goal. Preserve all old unknown/finality/history/source-stop facts. No shutdown or reboot.
