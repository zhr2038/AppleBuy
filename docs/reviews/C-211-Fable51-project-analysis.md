# Diagnosis: why it was hard, and whether the stack is wrong

**Facts about the three layers.** The repository contains three disconnected implementations. First, the offline core in `src/` is structurally unable to touch Apple: the engine constructor throws `RealActionBlocked` unless the port kind is "mock" in `src/engine.ts`, the runner repeats that guard in `src/runner.ts`, the real-port placeholder in `src/real-blocked.ts` is never wired, the DOM demo is scoped `fake-dom-only` in `src/app/dom-bridge.ts`, and the launch monitor accepts only synthetic samples. None of its plan schema, journal, ledger or slot policy is imported by the production path. Second, the production executor is the MV3 extension in `web/checkout-connector/`: one serialized function `merchantDocument` of 692 lines decodes every stage and performs every click, a 530-line `PurchaseJob` loop in `job.js` holds the write-ahead pending semantics, and `ChromePort` in `chrome-port.js` injects via `chrome.scripting.executeScript`. Third, the desktop program in `src/desktop/` drives that same job either through a Playwright-owned browser or through a native chain: Tk window, Node worker, Python broker, authenticated named pipe, Python native host, Chrome native messaging, extension RPC peer, then script injection. The real runs that reached PAYMENT and REVIEW used the native chain.

**Cause 1, wrong architectural choice: contract discovery by production stop.** The decoder requires exact structure for each stage, for example eight payment radios with a fixed ID grammar in `page-program.js:484-489`, a five-field contact form with exact types and maxlength at lines 461-464, and a pickup legend with specific class names at lines 177-184. Any deviation is UNKNOWN and the job gates to NEEDS_VERIFICATION or BLOCKED. The comment history inside the file shows the consequence: C019, C024, C029, C036, C044, C049, C050, C051, C064, C069, C149, C194, C204 and C205 each added rules after one real run exposed one new shape. The October 2 pilot by Codex browser tools walked the entire flow to an unpaid order in one afternoon, yet no sanitized structural capture of those pages was produced for fixtures. Both parties share this. Claude as reviewer repeatedly tightened exactness rules instead of demanding a complete read-only capture first. Codex implemented stop-by-stop adaptations instead of a capture tool.

**Cause 2, wrong failure mode for a dynamic page.** Every mutation gets a deadline of 8 seconds at `job.js:499`, and all waits after a mutation are bounded by that deadline at lines 292-295, 371 and 379. Through the native chain each read passes four process boundaries with their own timeouts, in `native-checkout-api.mjs`, `checkout_native_broker.py` and `checkout_native_host.py`. A slow secure-checkout render therefore ends as "mutation-result-unconfirmed" and requires a human resume. This is the direct source-level explanation for the C204 evidence that "several ordinary successor renders outlasted the current bounded read". The `AuthContinuation` watcher only covers the AUTH-to-checkout transition. Meanwhile the task window is 30 minutes at `job.js:161`, so two or three human resumes consume the window, which matches C197 and C204 ending in expiry. This is an architectural inference from code plus the recorded symptoms, not a measured trace.

**Cause 3, transport over-engineering.** The constraint "no cookie or profile copying, no security bypass" is correct, but the extension control page in `control.js` already satisfied it and could run the whole job in the user's Chrome. The desktop handoff in `desktop-handoff.js` then permanently revoked extension purchase authority on that record, forcing all later work through the native chain and the Tk app. That single decision multiplied the surface: owner leases through a Python child, archives with hard links, ticket files, pipe keys, and a dozen "unconfirmed" error classes.

**Cause 4, recovery machinery outgrew the happy path.** Because every real run ended in a stop with an unknown pending action, and because history may never be erased or resent, each new run needed a provable successor record. The result is four desktop recovery modules plus the extension-side probe, pre-final restart, retirement and rebind paths, each with its own schema and human attestation checkboxes. The Tk app now has twelve controls and five checkboxes. None of this exists for a user who wants one button.

**Cause 5, process and review overhead.** Docs are 7.5 MB against 487 KB of source. Status headings show the goal "actually blocked at the required handoff" at C179, C191 and C202, meaning code was accepted but could not be deployed without a human extension reload. Each change needed a task sheet, implementation, an Opus cross-review with exact command lists, manifest SHA checks, a bounded agreement and a publication record. "Quota takeover" comments throughout the code show the implementer switching mid-design.

**Cause 6, merchant facts and tooling, without anti-bot evidence.** Observed merchant behaviour: checkout sessions expire to a timeout page, a 30-minute payment window, the checkout host moves between secure subdomains, REVIEW omits store and slot and says the pickup date is determined after payment, and one real Add once returned a Page Not Found document while the bag held the item. Tooling: optional host permissions per subdomain, extension reload per code change, native host registration in HKCU, and Playwright loaded from a Codex runtime cache path in `purchase-worker.mjs:29`. I found no record of CAPTCHA or automation blocking in anything I read.

**Is the stack unsuitable, or is a slice missing?** Both, in a specific way. The platform works. The missing slice is real and small: no programme has ever submitted, so receipt and order-detail recognition in `page-program.js:302-316` and `lookupOrder` in `chrome-port.js:116-136` rest on historical order pages and guessed pending words. The smallest blocking cuts in the production graph, existing Pro first:

# Options, recommended route, and the first acceptance

**Option A, focused repair of the current executor.** Implement C209 inside the existing files: provenance-bound final consent, receipt from first real observation, longer settle waits, run from the extension control page. It reuses tested recognizers, but the monolithic decoder is hard to change safely, the control page refuses the handed-off record in `control.js:154`, and each change still needs the full review cadence. Expect two to three more cycles before a final.

**Option B, a clean small application on the person's normal browser session.** There are only two sanctioned ways to use a normal session without cookie copying or security weakening: an extension, or a separate program-owned profile where the person logs in once. Attaching a debugger to the personal Chrome requires a remote debugging flag, which is a security change to the personal browser and which recent Chrome versions refuse for the default profile. I reject that path. Both sanctioned ways already exist in this repository. The program-owned profile path in `browser-choice.mjs` and `browser-api.mjs` is simpler to iterate, but Playwright is an unverified prerequisite at a cache path, the person must log in again in that profile with possible repeated two-factor prompts, and no checkout step has been proved there.

**Option C, my choice: keep the extension platform, rewrite the control layer.** Technology: MV3 extension with a persistent content script registered for the shop paths on the granted apple.com.cn hosts, running in the ISOLATED world. The content script observes with a MutationObserver and reports stage facts to the extension page. The extension page holds a small linear stage machine and a journal in extension storage with export to a local file. Actions are message-driven clicks on recognized native controls. There is no native messaging, no Python, no desktop app and no online model. This keeps the person's session, keeps the supported browser API, handles login by waiting on a recognized AUTH stage until the person finishes, handles terms by one explicit consent on REVIEW, and is testable with fixture pages served locally plus the same content script. The Computer Use or vision-agent alternative is rejected: an online model on the critical path violates the requirements and is nondeterministic.

**Retain, freeze, remove, replace.**
- Keep: the extension platform and injection model; the observed selectors, IDs and labels distilled from `page-program.js` into per-stage recognizers; the pending-record semantics from `job.js`, namely durable intent before send, delivered versus untouched, never resend an unknown, one final per task; the Web Lock single owner in `owner.js`; the plan constants and hard caps.
- Freeze on disk, no further work: the offline core and DOM demo, the launch monitor, the old read-only connector, the Tk app, the native checkout chain and Python hosts, and the four desktop recovery modules. Their records and archives stay untouched.
- Remove from the MVP: order-summary disclosure reads, since the C204 fixture shows REVIEW states "数量 1" explicitly; the Duo prelaunch branch; rebind, retire, probe and pre-final restart flows; multi-browser selection.
- Replace: the monolithic decoder with per-stage recognizers; the 530-line loop with a linear existing-product sequence; fixed deadlines with a settle loop bounded by total elapsed time and by mutation count, never by resend.

**Preserving pending history.** The new executor writes to a new storage namespace and never touches the old extension key, the desktop task file or the archives. Before its first mutation it displays the old record digests and the retained unknown `continuePayment`, requires the person to confirm they reviewed the account order list, and itself reads the order list page read-only and refuses to proceed if a matching unpaid order is present. That preserves history without bypassing it.

## Independently checked Chrome documentation

Chrome documents ISOLATED-world and dynamically registered content scripts in [Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts). Registration applies scripts to eligible documents; a new document still needs its own initialization and identity checks. Chrome136 changed remote-debugging-port/pipe for the default data directory, as described in [Changes to remote debugging switches](https://developer.chrome.com/blog/remote-debugging-port). These are narrow platform facts, not proof of Apple order compatibility or a complete list of all possible supported control methods.
